## 3. Project explanation

A citizen uses a Java console client to report an emergency.

A central server validates and stores the report, then immediately notifies connected operators.

An operator reviews the report and assigns appropriate Police, Ambulance, and/or Fire & Rescue teams.

Each responder team receives its own assignment and sends progress updates.

The operator and reporting citizen receive updates through their existing TCP connections.

One incident may require several services. Each service progresses independently.

This is an academic prototype with fictional incidents and simulated teams. It does not contact actual agencies or dispatch real assistance.

Display at startup and before reporting:

“Academic demonstration — no real emergency dispatch.”

## 10. TCP framing and envelopes

Use four-byte big-endian length-prefixed UTF-8 JSON.

- Prefix length excludes the prefix itself.
- Maximum payload is 65,536 bytes.
- Read the exact prefix and payload.
- Handle partial reads and multiple consecutive frames.
- Reject invalid sizes before allocation.
- Handle malformed JSON and interrupted frames safely.

Envelope fields:

- version.
- kind: REQUEST, RESPONSE, EVENT.
- type.
- requestId for requests/responses.
- eventId for events.
- payload.
- ok for responses.
- structured error when unsuccessful.

Required request types:

REGISTER_CITIZEN
LOGIN
LOGOUT
GET_SNAPSHOT
CREATE_INCIDENT
GET_INCIDENT
LIST_INCIDENTS
LIST_TEAMS
SET_PRIORITY
ASSIGN_TEAM
CANCEL_ASSIGNMENT
RESPOND_ASSIGNMENT
UPDATE_ASSIGNMENT_STATUS
CLOSE_INCIDENT
REJECT_INCIDENT
SET_TEAM_AVAILABILITY
PING

Required events:

INCIDENT_CREATED
INCIDENT_UPDATED
ASSIGNMENT_OFFERED
ASSIGNMENT_UPDATED
TEAM_UPDATED

PING returns PONG.

Before authentication, allow only registration, login, and heartbeat.

Every business request returns a success response or structured error.

Error codes:

VALIDATION_ERROR
UNAUTHENTICATED
FORBIDDEN
NOT_FOUND
TEAM_UNAVAILABLE
ACTIVE_ASSIGNMENT_EXISTS
INVALID_TRANSITION
VERSION_CONFLICT
IDEMPOTENCY_CONFLICT
UNSUPPORTED_VERSION
INTERNAL_ERROR

Use one writer per connection and an outgoing queue bounded to 100 frames.

A persistently slow client must not block healthy sessions or consume unlimited memory.

## 12. Authentication and security

- Use salted PBKDF2WithHmacSHA256 password hashes.
- Use random salts of at least 16 bytes.
- Initially configure 600,000 iterations; measure and document cost.
- Use constant-time comparison.
- Return generic invalid-credential errors.
- Permit one active session per user.
- A new successful login explicitly replaces and notifies the old session.
- Never log passwords or full sensitive message dumps.
- Restrict notification recipients and response fields by role.

Use fictional data on localhost or a trusted LAN.

Plain TCP is unencrypted. Public deployment and TLS provisioning are outside scope.

## 13. State rules

### Incident

REPORTED → ACTIVE when the first assignment is offered.

REPORTED → REJECTED only if it has never had an assignment.

ACTIVE → CLOSED only by an operator when:

- At least one assignment is COMPLETED.
- Every assignment is terminal.

CLOSED and REJECTED are terminal.

An ACTIVE incident with all offers declined/cancelled remains visible as needing assignment.

### Assignment

OFFERED → ACCEPTED or DECLINED.

ACCEPTED → EN_ROUTE → ARRIVED → COMPLETED.

Operators can cancel OFFERED or ACCEPTED assignments with a reason.

Do not cancel EN_ROUTE or ARRIVED assignments.

DECLINED, CANCELLED, and COMPLETED are terminal.

Reject skipped, backward, stale, and unauthorized transitions.

### Team availability

AVAILABLE, BUSY, UNAVAILABLE.

Offering an assignment immediately reserves the team as BUSY.

A terminal assignment releases the reservation and returns the team to AVAILABLE.

A responder can change AVAILABLE/UNAVAILABLE only without an active assignment.

### Presence

ONLINE or OFFLINE.

Assign only ONLINE and AVAILABLE teams.

A disconnected BUSY team remains reserved. Do not automatically free or reassign it.

On restart, presence starts OFFLINE and active assignments continue to determine BUSY status.

## 14. Concurrency, revisions, and idempotency

Use expectedRevision for mutable entities and check it atomically.

Return VERSION_CONFLICT for stale updates. The client refreshes and asks the user to review before retrying a changed action.

For authenticated business mutations:

- Deduplicate by user ID and request ID.
- Canonically hash request type and payload.
- Persist the successful response atomically with the business change.
- Identical retries return the original result.
- Different content with the same ID returns IDEMPOTENCY_CONFLICT.

Registration and login/logout require appropriate account/session handling; replaying a stored response must not incorrectly authenticate a new socket.

Acknowledge only after commit.

Notify after commit.

A notification failure does not reverse committed data.

After a 10-second timeout, show confirmation pending. Retain the original request ID for reconciliation/retry.

Do not claim exactly-once network delivery.

## 15. Recovery

- Send heartbeat every 15 seconds.
- Detect loss after 45 seconds without inbound activity.
- Reconnect with 1, 2, 4, 8, then up to 15 seconds delay with jitter.
- Require login again.
- Fetch a fresh authorized snapshot.
- Subscribe authenticated sessions to events before snapshot creation.
- Buffer events while synchronizing.
- Ignore older revisions.
- Retain unsent report input.
- Restore reserved assignments after reconnect.
- Close sockets, threads, and database resources cleanly.

Persistent offline event delivery is not required.
